# E1: First measured Flink comparison: ETL pipeline, FIT workload (FD vs FMAX + parallelism grid)

**Reproduces:** STREAMLINE §5.1.1 (ETL, FIT dataset), baselines FD and FMAX. STREAMLINE itself is evaluated in E3 (`E3_RESULTS.md`); latency below capacity is in L1 (`L1_RESULTS.md`).
**Code:** the authors' benchmark `beam-applications-java` @ `57524e2`, unmodified. Every environment deviation is listed in `ENVIRONMENT_AND_MODIFICATIONS.md`.
**Data:**
- `results/E1_fit_r4000/*.json`: raw 5 s time series, placement and summaries
- `results/E1_fit_r4000/summary.md`: generated by `scripts/analyse_e1.py`
- the original repetition 1, run on battery, is kept in `results/battery_or_standby/E1_fit_r4000/` and not used

## 1. Setup

| Item | Value |
|---|---|
| Cluster | k3d on one laptop; Flink 1.18.1 session cluster, 4 TaskManagers × (1 CPU, 2 GiB, 2 slots) = 8 slots; Kafka 3.7.0 (1 broker, topics with 1 partition as in the authors' chart); MongoDB 7 |
| Pipeline | ETL (RIoTBench) for FIT, written in Apache Beam, run with Beam's FlinkRunner. It becomes 2 Flink vertices: [Kafka source → parse] and [Interpolate (`GroupIntoBatches`) → annotate → serialise → Kafka + MongoDB sinks] |
| Workload | MHEALTH (FIT) through the authors' `senMlConverter`, replayed with the authors' `KafkaProducer`. Nominal 4000 el/s; **achieved 2620–2641 el/s**, which is above every configuration's capacity, so every run is saturated and throughput measures capacity |
| Configurations | FD = Flink default parallelism 1 · p = 2 · p = 4 · FMAX = p = 8 (all slots). Parallelism is job-wide, the only option Beam's FlinkRunner exposes |
| Protocol | Fresh TaskManager JVMs per run · 360 s run · first 150 s discarded (JIT warm-up) · metrics every 5 s · 3 repetitions, interleaved by repetition · all runs on AC power |
| Metrics | Throughput = Flink REST `numRecordsOutPerSecond` of the source vertex. CPU = pod CPU (metrics.k8s.io). Cost = TaskManagers used × $0.192/h (paper Table 1, type 1) |

**Measurement notes:**
- **Latency is not interpreted in E1.** Its marker quantiles use Flink's default 128-marker history at a 5 s interval (~640 s), so they include warm-up markers. And under saturation, markers exclude time spent waiting in Kafka. Latency is measured properly in L1 and E3.
- **Effective rate.** The authors' producer replays only 4 of every 5 events (ENVIRONMENT §9). E1 reports measured (achieved) rates throughout, so its numbers are unaffected.
- **Repetition 1 was re-measured.** It first ran on battery: CPU per record was 1.08–1.26 ms vs 0.92–0.98 on AC, and throughput was ~20% lower in every configuration (ENVIRONMENT §13). It was re-measured on AC on 11-06. Since E1, the latency history, metrics fetcher interval and slot timeout have been changed (ENVIRONMENT §7). None of these affects the throughput meters. The re-run used slightly more CPU per record (1.01–1.02 ms), with host load from other processes at 4.0–4.5 cores.

| Config | TMs used | Throughput (el/s) | TM CPU (cores) | CPU utilisation of used TMs | Cost ($/h) |
|---|---|---|---|---|---|
| **FD** (p = 1) | 1 | **1115 ± 32** | 1.06 | 1.06 | **0.192** |
| p = 2 | 1 | 1100 ± 30 | 1.06 | 1.06 | 0.192 |
| p = 4 | 2 | 1478 ± 344 | 1.43 | 0.71 | 0.384 |
| **FMAX** (p = 8) | 4 | 1473 ± 314 | 1.45 | 0.36 | **0.768** |

The busiest Interpolate subtask ran at **1000 ms/s busy (100%) in all 12 runs**, so it is the bottleneck in every configuration.

### Placement explains the variance

Recorded per run: whether the active source subtask and the single busy Interpolate subtask share a TaskManager, i.e. one CPU.

| Hot subtasks | Runs | Throughput (el/s) |
|---|---|---|
| Same TaskManager (all p = 1 and p = 2 runs, p = 4 rep 1, FMAX rep 2) | 8 | 1067–1141 (mean 1096 for p > 2) |
| Different TaskManagers (p = 4 reps 2–3, FMAX reps 1 and 3) | 4 | 1630–1684 (mean 1665) |

The large SDs at p = 4 and FMAX are entirely placement. FMAX rep 2 placed both hot subtasks on one TaskManager and reached
**1111 el/s, the same as FD**, at 4× the cost.

## 4. What this means for the reproduction (critical analysis)

1. **The benchmark structurally limits what parallelism can do.** `Interpolate` keys every record with the same constant (`WithKeys.of("")`), so a single subtask processes the whole stream after the source. The input topic has 1 partition. Raising parallelism from 1 to 8 does not add processing capacity to the bottleneck, which is 100% busy in every run. The only gain comes from giving that subtask **its own CPU**, i.e. placement.
2. **The gain from more parallelism is a side effect of placement.** Flink's slot assignment decides whether the two hot subtasks are separated, and it varied between runs: FMAX was separated in 2 of 3, p = 4 in 2 of 3. The paper reports FMAX within 1% of STREAMLINE. Our data says that holds only when placement happens to separate the hot subtasks.
3. **The paper's resource-efficiency argument is supported in principle.** The cheapest configuration that reaches maximum throughput uses 2 TaskManagers, not 4. Beam's FlinkRunner, however, cannot express per-operator placement or parallelism, so STREAMLINE's decisions can be applied only approximately (job-wide parallelism plus TaskManager count; see E3).
4. **Repeatability:** single-run differences of ±50% come from placement. Reproductions of this paper need recorded placement, recorded power state and repeated runs. The paper reports averages of 3 runs without placement information.

## 5. Limitations

- One laptop. Each TaskManager = 1 core (paper type 1 = 4 cores), so absolute numbers are not comparable; only relative ones.
- Kafka has 1 broker (the paper's chart uses 3). The producer reaches only ~66% of the nominal rate (2630/4000 el/s), which is still above capacity.
- Parallelism is job-wide only (Beam). Per-operator CPU is not separable (fused operator chains), so pod CPU is used instead.
- Repetition 1 was measured a day after repetitions 2–3, under the later cluster configuration and slightly higher host load (§1).
- The placement stratification is post hoc: n = 4 separated vs 8 co-located.
- Earlier pilot data (leaky TaskManagers; 60 s warm-up design; all on battery) is excluded and kept only as documented pilot/design checks.

## Correction (2026-11-13): CPU utilisation of used TaskManagers

The column "CPU utilisation of used TMs" above divides the summed CPU of **all four** TaskManager pods by the number of
TaskManagers hosting tasks. For p = 1, 2 and 4 the idle TaskManagers' background CPU (~0.02–0.05 core each) is therefore in the
numerator but not the denominator, which is why FD reads above 1.0 although its busy TaskManager never exceeded its 1-CPU limit
(max 0.99–1.00 core). Recomputed for the TaskManagers that host tasks only (`scripts/cpu_util_used_only.py`, output
`results/cpu_util_used_only.md`): FIT FD 1.00, p = 2 1.00, p = 4 0.69, FMAX 0.36; TAXI FD 1.00, p = 2 0.99, p = 4 0.60, FMAX 0.40.
The report (Table 4) uses the recomputed values. The FD-vs-FMAX conclusion is unchanged.
