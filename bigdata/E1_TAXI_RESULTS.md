# E1-TAXI: ETL pipeline, TAXI workload, saturated capacity (FD vs FMAX + parallelism grid)

**Reproduces:** STREAMLINE §5.1.1 (ETL, TAXI dataset), baselines FD and FMAX. This is the TAXI counterpart of E1 on FIT (`E1_RESULTS.md`), with the same protocol.
**Code:** the authors' benchmark `beam-applications-java` @ `57524e2`, unmodified. The ETL variant is selected with the authors' own `--experiRunId=TAXI`. Environment deviations are listed in `ENVIRONMENT_AND_MODIFICATIONS.md`; the TAXI replay file is described in §5.
**Data:**
- `results/E1_taxi_r3500/*.json`: raw 5 s time series, placement, power record and summary for each run
- `results/E1_taxi_r3500/summary.md`: generated by `scripts/analyse_e1.py`
- the 8000 el/s pilot run is not used (see §1)

All numbers below are measured in this reproduction. Numbers from the paper are labelled as such.

## 1. Setup

| Item | Value |
|---|---|
| Cluster | Same as E1: k3d, Flink 1.18.1, 4 TaskManagers × (1 CPU, 2 GiB, 2 slots); Kafka 3.7.0 (1 broker, 1-partition topics); MongoDB 7 |
| Pipeline | ETL for TAXI (RIoTBench), written in Beam and run with the FlinkRunner. Like FIT, it becomes 2 Flink vertices, and `Interpolate` keys every record with one constant key |
| Workload | One week of NYC taxi trips (2013-01-14 to 01-21), converted by the authors' `senMlConverter`. **Constant-rate replay**: the first 1.5 M events in pickup order, with the delay column replaced by a nominal 3500 el/s schedule (`scripts/make_taxi_rate_file.py`; payload unchanged). Achieved input: **2724–2742 el/s**, above every configuration's capacity, so every run is saturated |
| Why 3500 el/s | A pilot at nominal 8000 el/s (6240 achieved) put 9.3 cores of host load on the laptop (producer and port-forward). p = 8 then processed only 1639 el/s, against 1969 at 3500. At 3500, host load returned to the normal 4.0–5.1 cores |
| Configurations | FD (p = 1) · p = 2 · p = 4 · FMAX (p = 8). Job-wide parallelism only |
| Protocol | Fresh TaskManagers per run · 360 s run · first 150 s discarded · 5 s metrics · 3 repetitions, interleaved by repetition · power guard (ENVIRONMENT §13) |
| Run validity | All 12 runs: AC power from start to end, no sleep or standby events, first attempt, job RUNNING throughout, no exceptions. Host load from other processes: mean 4.0–5.1 cores per run |

## 2. Results (mean ± SD over 3 repetitions)

| Config | TMs used | Throughput (el/s) | TM CPU (cores) | CPU utilisation of used TMs | CPU per record (ms) | Cost ($/h) |
|---|---|---|---|---|---|---|
| **FD** (p = 1) | 1 | **1337 ± 12** | 1.10 | 1.10 | 0.82 | **0.192** |
| p = 2 | 1 | 1296 ± 14 | 1.12 | 1.12 | 0.86 | 0.192 |
| p = 4 | 2 | 1528 ± 365 | 1.28 | 0.64 | 0.84 | 0.384 |
| **FMAX** (p = 8) | 4 | **1959 ± 16** | 1.62 | 0.40 | 0.83 | **0.768** |

The busiest Interpolate subtask ran at 999–1000 ms/s busy (100%) in all 12 runs, so it is the bottleneck in every configuration, as on FIT.

**FD vs FMAX: throughput −31.7%. FMAX costs 4.0× as much, and its CPU utilisation is 0.40 against FD's 1.10.**

### Placement explains the variance again

| Hot subtasks (active source, busiest Interpolate) | Runs | Throughput (el/s) |
|---|---|---|
| Same TaskManager (all p = 1 and p = 2 runs; p = 4 reps 1–2) | 8 | 1283–1349 |
| Different TaskManagers (p = 4 rep 3; FMAX reps 1–3) | 4 | 1940–1969 (mean 1956) |

This time FMAX separated the two hot subtasks in all 3 runs, so its SD is small. p = 4 separated them only in rep 3: 1948 el/s at half of FMAX's cost. The other two p = 4 runs gave 1288 and 1348, the same as FD.

### TAXI vs FIT (both measured here, same cluster and protocol)

| Quantity | FIT (E1) | TAXI (E1-TAXI) |
|---|---|---|
| FD throughput | 1115 el/s | 1337 el/s |
| Throughput with separated hot subtasks | 1665 el/s | 1956 el/s |
| Gain from separation | +49% | +46% |
| FD vs FMAX (all runs) | −24% | −32% |
| CPU per record | 0.92–1.02 ms | 0.82–0.86 ms |

TAXI records are about 15–20% cheaper to process than FIT records, so every configuration is faster. The structure is identical, though: a single hot subtask caps throughput, and only separating it from the source helps. The FD-vs-FMAX gap differs between datasets (−24% vs −32%) only because FMAX happened to be co-located in 1 of 3 FIT runs and in 0 of 3 TAXI runs. Against separated runs only, the gap is −33% on FIT and −32% on TAXI.

One small effect: on TAXI, p = 2 is 3% slower than p = 1 (1296 vs 1337, about 3 SDs with n = 3). FIT points the same way (1100 vs 1115), but that difference is within its noise (SD 30). A plausible cause is the extra network-stack serialisation between two subtasks in one JVM that p = 1's operator chain avoids. We did not test this.

## 3. Comparison with the paper (relative outcomes; TAXI, §5.1.1)

| Statement in the paper (TAXI) | Paper | This reproduction | Agreement |
|---|---|---|---|
| FD has lower throughput than STREAMLINE, with STREAMLINE ≈ FMAX (within 1%) | FD **−14%** average | FD vs FMAX capacity: **−32%** | Same direction. The magnitudes measure different things (see below) |
| FD "handled low TAXI workloads but struggled at higher rates" | Qualitative | FD's capacity is 68% of FMAX's. Whenever the input is below 1337 el/s, FD processes all of it | **Consistent** with the mechanism |
| FD achieves better CPU utilisation than FMAX; FMAX has the poorest efficiency | Qualitative | FD 1.10 vs FMAX 0.40 | **Consistent** |
| Average end-to-end latency of FD and FMAX differs by under 4% | < 4% | Not measured (saturated runs; see E1 §1 and L1) | — |
| STREAMLINE cost −51% vs FD and −67% vs FMAX; runs on a single type-2 instance | −51% / −67% | STREAMLINE not run on TAXI. The cheapest configuration that reached FMAX-level throughput was p = 4 on 2 TMs (−50% vs FMAX), and that happened in 1 of 3 runs | Not reproduced |

**Why −14% and −32% are not in conflict.** The paper replays TAXI's real, fluctuating arrival pattern (1,000–10,000 el/s, scaled as recommended for RIoTBench). FD keeps up during low periods and falls behind only at peaks, so its throughput averaged over time is close to the input rate for much of the run. Our runs feed every configuration above its capacity the whole time, so the measured gap is the largest possible: an upper bound for the paper's time-averaged gap. If the paper's FD capacity relative to FMAX were similar to ours (68%), a −14% average would mean the workload exceeded FD's capacity for only part of the run. That fits the paper's description of fluctuating TAXI peaks, but we cannot check it, because the paper does not publish its TAXI rate trace.

## 4. Critical analysis

1. **The single-hot-key limit is not FIT-specific.** The TAXI ETL variant has the same `WithKeys.of("")` bottleneck and the same 2-vertex job, and the same 100%-busy subtask. Capacity is decided by placement, not parallelism: the jump from ~1320 to ~1956 el/s happens exactly when the two hot subtasks land on different TaskManagers, at any p > 2.
2. **The paper's FMAX ≈ STREAMLINE result depends on placement here too.** FMAX was separated in 3/3 TAXI runs but 2/3 FIT runs. Across all p = 8 runs in this project, including E3, 3 of 18 were co-located. A single unlucky placement erases the advantage of 4× the resources.
3. **A cheaper configuration with full throughput exists** (p = 4, 2 TMs) but is reached only if placement is favourable. A tuner that cannot control placement, as with Beam's FlinkRunner, cannot reliably obtain the paper's cost savings on this pipeline.

## 5. Limitations

- **Constant-rate replay.** The real TAXI arrival pattern is discarded. This is valid for capacity measurement, but it is not the paper's workload. Latency and time-averaged throughput under the real pattern are not reproduced.
- The input rate (2730 el/s) is far below the paper's TAXI peaks (10,000 el/s), because one laptop cannot generate more without disturbing the measurement (§1).
- One laptop with 1-core TaskManagers, 1 Kafka broker and job-wide parallelism only, as in E1 §5.
- n = 3 per configuration. The placement stratification is post hoc (4 separated vs 8 co-located).
